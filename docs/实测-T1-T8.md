# Orbis 真机实测记录（T1–T8）

> **使用方式**：在 Windows 开发机上逐项填写，每项完成后回写 `pm/04-技术设计.md` 的对应章节
> 或 `pm/Phase0-*` 记录增补。**不要改本模板的结构**，只填内容。
>
> **为什么必须有这份记录**：`data/` 与 `orbis-providers/` 里的常量一旦是「推测值」，
> 就会静默产生错误行为（例如错误的国服 API base 会让更新检测恒为 Unknown，
> 而用户看到的只是「暂无更新」）。实测记录是把推测值换成证据链的唯一途径。

## T4a · 解锁器提权必要性（最高优先）

**决定**：04 §3.3 权限模型 / §5.9 编排方案 / Manifest `requires_admin` / §11 Q6 / **可能触发 02 B7+B8 返工**

**方法**：在**亲子模型**假设下（解锁器作为父进程，创建挂起的游戏子进程，注入后恢复），
验证解锁器是否仍需管理员权限。

| 观测点 | 记录 |
|--------|------|
| 解锁器自身是否需要管理员？ | |
| 亲子模型下是否免去提权？ | |
| UAC 弹窗出现次数（每次启动 / 仅首次 / 无） | |
| 无提权时游戏是否正常启动 | |
| 无提权时 120 FPS 是否生效（游戏内实测） | |
| 反作弊是否介入（进程被踢 / 报错 / 无异常） | |

**结论**：□ 亲子模型免提权 → 方案 A 成立，`requires_admin = false`
□ 必须提权 → 记录弹窗频次，**并评估是否与 02 B8 冲突**
□ 其它（说明）：

**回写目标**：04 §3.3 / §5.9 / `data/tools/manifests/genshin-fps-unlock.json` 的
`requires_admin` 与 `pending_verifications`（移除已收敛项）；若冲突则回 02 评审。

## 附录：实测记录质量要求

1. **原始值优先**：版本号、路径、键名一律记**逐字原文**，不要写「大概是」
2. **证据可校验**：涉及外部接口的项必须附抓包文件 / 社区来源链接；涉及写入的项必须附前后截图或哈希
3. **失败也要记**：写「不可行 + 现象」比留空有价值 —— 留空会被后人误读为「还没做」
4. **安全前置不可省**：任何涉及写入游戏文件的项，先备份、先断网、先确认反作弊状态
5. **结论要能执行**：每项结论必须能直接翻译成「改哪个文件的哪个值」，否则回去补测
