## 1. P1 `getInstallationDetail` 重入锁死锁

### 1.1 证据链（已逐环确认）

1. `commands.rs:457` `state.with_db(|db| { ... })` —— `with_db`（`commands.rs:101-111`）执行
   `self.db.lock()` 并把 guard **持有到闭包返回**。
2. 闭包内 `commands.rs:460` 定义 `let is_enabled = |tool_id: &str| state.tool_enabled(tool_id);`
3. `commands.rs:472` 把它交给 `orbis_tools::list_tools(state.data(), Some(&record.game_id), &is_enabled)`。
4. `orbis-tools/src/contract.rs` 的 `list_tools` 对**每个** manifest 求值
   `is_enabled(manifest.id.as_str())`（`filter(...).map(|m| tool_dto(..., is_enabled(m.id.as_str())))`）。
5. `is_enabled` → `AppState::tool_enabled`（`commands.rs:119-136`）→ `commands.rs:120` `self.db.lock()`。

`std::sync::Mutex` **不可重入**（`lock` 文档：已持有者再次调用会阻塞/panic）。同一线程重入 → 永久阻塞。

### 1.2 触发条件是确定的，不是偶发

`list_tools` 先 `filter` 后 `map`，因此只有当**该游戏存在 manifest** 时回调才会被调用：

- `data/tools/manifests/genshin-fps-unlock.json` → `game = genshin-impact`
- `data/tools/manifests/wuwa-fps-120.json` → `game = wuthering-waves`

→ **打开原神或鸣潮的详情页 = 100% 死锁**。其余 3 款游戏无 manifest，filter 后为空，不触发回调。

### 1.3 放大效应（比「一条命令卡住」严重）

guard 永不释放 → `db` 锁被永久占用 →
- `commands.rs:173`（`poll_runtime_changes`，5 秒周期）随之阻塞；
- 所有 `with_db` 命令（`listInstallations` / `getSettings` / `setSetting` / `getLaunchProfile` /
  `setLaunchProfile` / `resetLaunchProfile` / `removeInstallation` / `getInstallationDetail`）排队。
→ **一次点击，约 5 秒内后端全面冻结。**

### 1.4 为什么现有防线全部漏掉

- `commands.rs` 的 26 个测试**没有一个调用 `#[tauri::command]` 函数**（只测 `with_db` /
  `tool_enabled` / `latest_version_norm` 等内部件），因此命令级接线从未被执行；
- `ci.yml` 的 `shell` job（行 162-165）只跑 `cargo check -p orbis`，**不跑 `cargo test`**
  → 即便有命令级测试也不会在 CI 执行。

两者叠加使该缺陷对本地与 CI 同时隐形。

### 1.5 影响面唯一性（已逐点核对）

`commands.rs` 共 14 个 `with_db(|db| ...)` 调用点，逐一核对闭包内是否调用了会再次加锁的方法：
**只有 `getInstallationDetail` 一处**。`listTools`（`commands.rs` 内）也调用 `state.tool_enabled`，
但它不在 `with_db` 之内 → 安全。`poll_runtime_changes` 在持锁期间调用 `self.observe_playtime(db, ...)`
传的是 `&Db` → 安全；随后取 `last_runtime` 锁，方向固定（`db → last_runtime`），无反向路径。
**P1 是全仓唯一例外** —— 它不是「嵌套取另一把锁」（会被锁序审查抓住），而是「重入同一把锁」，
这正是它逃过长列表审查的原因。

### 1.6 修复方案

**原则**：不要靠「记得别在持锁时调自锁方法」——那依赖人的注意力。改为**让重入在结构上难以发生**，
并**让重入一旦发生就必然被测试抓到**。

**步骤 1｜拆分锁语义（消除重入可能）**

把「读工具启用状态」拆成两档，其中一档不自己加锁：

```rust
/// 已持锁调用点用这个：不自己加锁（db 由调用方保证）。
fn tool_enabled_with(&self, db: &Db, tool_id: &str) -> bool { /* 只做查询 + 降级留痕 */ }

/// 未持锁调用点用这个。
fn tool_enabled(&self, tool_id: &str) -> bool {
    let Ok(guard) = self.db.lock() else { /* 留痕 */ return false; };
    guard.as_ref().is_some_and(|db| self.tool_enabled_with(db, tool_id))
}
```

`getInstallationDetail` 的闭包改为 `|tool_id| state.tool_enabled_with(db, tool_id)`。
`listTools` 保持调用 `tool_enabled`（自锁版）不变。

同时在 `orbis-tools::list_tools` 的 `is_enabled: &dyn Fn(&str) -> bool` 参数上补一条文档注释：
**「该回调不得获取任何锁」** —— 类型系统表达不了这个约束，只能靠注释 + 测试兜住。

**不做的事**：不换 `parking_lot::ReentrantMutex`。可重入锁会把这个 bug 从「死锁」降级为「锁语义
混乱下读到中间状态」，把确定性故障变成偶发故障，方向相反。

**步骤 2｜引入可测接缝**

命令体抽为接收 `&AppState` 的普通函数，`#[tauri::command]` 只做转发：

```rust
fn installation_detail(state: &AppState, installation_id: &str)
    -> OrbisResult<InstallationDetailDto> { /* 原闭包体 */ }

#[tauri::command]
pub fn getInstallationDetail(state: State<'_, AppState>, installationId: String)
    -> OrbisResult<InstallationDetailDto> { installation_detail(state.inner(), &installationId) }
```

这样测试能直接构造 `AppState` 调用命令体 —— **这是唯一能在 CI 上覆盖命令接线的办法**。
建议对「多步装配」型命令（`listInstallations` / `getInstallationDetail` / `getCompatibility`）
统一施加这个模式，但可分批。

**步骤 3｜死锁回归测试（本方案最重要的资产）**

用 watchdog 线程 + `recv_timeout`：真死锁时测试在 5 秒内 **失败**，而不是挂起 CI。

```rust
#[test]
fn installation_detail_does_not_deadlock_on_its_own_lock() {
    // 关键：测试数据必须包含「属于该游戏的 manifest」。
    // 用空 manifest 会让 list_tools 的 filter 产出空集 → 回调不被调用 → 死锁不暴露（假绿灯）。
    let state = AppState::new(data_with_manifest_for("genshin-impact"), Some(db_in_temp()), true);
    let (tx, rx) = std::sync::mpsc::channel();
    std::thread::spawn(move || { let _ = tx.send(installation_detail(&state, "i1")); });
    match rx.recv_timeout(std::time::Duration::from_secs(5)) {
        Ok(res) => assert!(res.is_ok(), "应正常返回该实例的详情"),
        Err(_) => panic!("installation_detail 5 秒内未返回 —— 十有八九重入了 db 锁"),
    }
}
```

**验收口径**：把步骤 1 的修复临时回退，该测试必须在 5 秒内变红；恢复修复后变绿。
（这是判断测试是否真的覆盖了该路径的唯一可靠方法 —— 不能用「测试通过」当作覆盖证明。）

**可选加固（不阻塞本次）**：把 `db.lock()` 私有化，只允许 `with_db` 与 `*_with(db, ..)` 访问，
迫使全部读路径显式二选一，从结构上消灭重入。改动面涉及 `poll_runtime_changes` /
`try_installations`，建议单独立项。

## 2. P2-2 `process.rs` 路径匹配

### 2.1 复核：性质与审计描述不同

审计说「前缀匹配没有分隔符边界 → 误报」。复核后**风险方向颠倒了**：

- **误报**（审计所述）：需要 `record.executable_path` 是**目录**或短路径。而该字段按契约 §6
  （`executablePath: string`）与 04 §6.1（`installation.executable_path UNIQUE`）的语义是
  **可执行文件路径**，且只由 `addInstallation` 写入 —— 该命令**尚未实现**，库里没有任何真实行。
  所以目前不构成现实缺陷。**但** `process.rs:152` 的测试主动断言
  `find_running("C:/Games/Sample/game")` 命中 `C:/Games/Sample/game.exe`，
  即把这条宽松语义**固化成期望行为** —— 它会误导后续实现者，且没有任何文档依据
  （04 §5.10 只说「匹配 = exe 路径前缀」，未定义边界）。
- **漏报**（审计未提，更现实）：比较前**未归一化**，有两处真实缺口：
  1. **分隔符**：用户在文件对话框若得到 `C:/Games/x.exe`（正斜杠），而 `sysinfo` 返回
     `C:\Games\x.exe` → `starts_with` 失败 → **游戏在运行却显示「未运行」**，
     连带时长不统计、状态不更新。这是**静默降级**，直接违反 04 §8「禁止静默失败」。
  2. **`\\?\` 长路径前缀**：一侧有、一侧无即不匹配 → 同上漏报。

  大小写已在 Windows 分支归一（`to_lowercase`），这一点审计未提及，实现是**正确**的。

### 2.2 修复方案

**先改文档再改实现**（沿用 Q11 的纪律：04 是已定稿的设计决定，口径变更须先在 04 精确化）。

1. **04 §5.10 把「前缀」精确定义**为：*「以路径分隔符为界的前缀」* ——
   即「完全相等」或「以 `记录值 + 分隔符` 开头」。补充说明其目的是容忍同一 exe 的多种报告形态，
   而不是「同一目录下的任意 exe」。
2. **实现**：`path_matches` 增加归一化（剥离 `\\?\` 前缀、统一分隔符）+ 组件边界判定：

   ```rust
   fn path_matches(process_exe: &str, recorded_exe: &str) -> bool {
       // 1) 归一化：剥离 \\?\、统一分隔符、平台相关大小写
       // 2) 相等 → true
       // 3) 记录值视为目录前缀时，要求以「记录值 + 分隔符」开头
   }
   ```
3. **测试调整**：删除 `process.rs:152` 那条把「同级文件名前缀命中」当期望的断言，替换为：
   - `C:\Games\Foo\game.exe` vs `C:\Games\Foo\game.exe.bak` → 不命中（现已正确，保留）
   - `C:\Games\Endfield` vs `C:\Games\Endfield2\game.exe` → **不命中**（修复后新增）
   - `C:\Games\Foo` vs `C:\Games\Foo\game.exe` → 命中（目录前缀，以分隔符为界）
   - `\\?\C:\Games\Foo\game.exe` vs `C:\Games\Foo\game.exe` → 命中（归一化后新增）
   - `C:/Games/Foo/game.exe` vs `C:\Games\Foo\game.exe` → 命中（分隔符归一后新增）

**注意**：这是**行为变更**（收紧判据），且 `find_running` 目前被 `dto.rs::runtime_states` 与
A6 会话跟踪共用，改动需同时跑通两侧测试。

## 3. P2-3 `NOT_IMPLEMENTED` 无产生路径

### 3.1 复核：成立

- 契约 §7.1（`:612`）明文：`src/api/tauri.ts ← invoke 实现（未实现命令抛 NOT_IMPLEMENTED）`。
- `NOT_IMPLEMENTED` 定义齐备：契约 §5:363（注「开发期占位，**发布前必须为 0 处**」）、
  `types.ts:120`、`src/utils/errorMessages.ts:191`。
  （审计写的路径 `src/api/errorMessages.ts` 有误，实际在 **`src/utils/`**。）
- 但 `tauri.ts:26-37` 的 `normalizeError` 把「非对象拒绝」归为 `INTERNAL`；Tauri 对未注册命令
  拒绝的是字符串 → 全仓**没有任何代码路径产生 `NOT_IMPLEMENTED`**。
- 影响：`npm run tauri dev` 下，18 条未实现命令全部呈现为「出了点问题 + 重试」，
  而契约的意图是「功能开发中」。生产包不受影响（`release.yml:66` 强制 `VITE_ORBIS_API=mock`）。

### 3.2 三个方案供裁决

| 方案 | 做法 | 优点 | 代价 |
|------|------|------|------|
| **A** | Rust 侧注册 18 个占位命令，返回 `NOT_IMPLEMENTED` | 前端零改动 | ①与「发布前必须为 0 处」冲突，需人工删；②`generate_handler!` 被假命令污染；③UI 可能误判「已实现」 |
| **B（推荐）** | `tauri.ts` 维护「已实现命令」集合，`invokeCmd` 查表命中才发 IPC，否则直接抛 `NOT_IMPLEMENTED` | 契约 §7.1 正是把这个责任放在 `tauri.ts`；Rust 侧不动 | 白名单会与 `generate_handler!` 漂移 → 需配一条断言 |
| **C** | 等 `tauri-specta`（Q3 已拍板未执行） | 生成物天然知道命令是否存在，无需手工白名单 | 属另一个切片的产出，现在不能立刻兑现 |

**选 B 时的防漂移做法**：加一条断言（`check-architecture.sh` 或 Rust 单测），
比对 `tauri.ts` 白名单与 `lib.rs::generate_handler!` 的命令列表。否则就是把「静默漂移」
从 catalog 搬到了命令表。

## 4. P2-4 catalog 双源漂移

### 4.1 复核：成立，当前值一致

- `src/api/mock.ts:178` `GAME_CATALOG`：5 条，含**硬编码** `hasBundledComponent: true/false`。
- `crates/orbis-providers/src/catalog.rs`：5 条，**无** `hasBundledComponent` ——
  由 `dto.rs:57` 从 Manifest 派生：`manifests.for_game(id).any(|m| m.requires_asset())`，
  而 `requires_asset()` = `entry.asset.is_some()`（`manifest.rs:230`）。
- **逐项核对当前一致**：id / name / enName / publisher / regions / officialUrl 全同；
  - `genshin-fps-unlock.json` → `entry.asset = "genshin-fps-unlock"` → 派生 `true` = mock `true` ✓
  - `wuwa-fps-120.json` → `entry` 无 `asset` → 派生 `false` = mock `false` ✓
- **无任何自动检查**。`check-architecture.sh` 的 [8]（`:132`）只扫 `src/views` 与 `src/store`，
  **不扫 `src/api/mock.ts`**（mock 作为参照实现必须有目录数据，这是允许的）。

结论：不是现存分叉，是**漂移风险**。最脆的一环是 `hasBundledComponent` ——
它由 `entry.asset` 派生，**改一个 manifest 就会让 mock 静默失真**。

### 4.2 三个方案供裁决

| 方案 | 做法 | 评价 |
|------|------|------|
| A | 断言固化：把 5 条 officialUrl / hasBundledComponent 写进 `smoke-render.mjs` | 只能验 mock 自身，**抓不到 mock 与 Rust 的不一致**（不解决目标问题） |
| **B（推荐）** | 新增 `scripts/check-catalog-parity.mjs`，被 `verify` / `check:arch` 调用 | 三方对齐：Rust `catalog.rs` = mock `GAME_CATALOG` = `data/tools/manifests/*.json` 现算的期望值 |
| C | 目录抽成 `data/catalog/games.json` 单源；Rust 用 `build.rs` 生成 const，mock 直接 import | 根治，但引入 `build.rs` 新机制、改变 catalog 的「编译期常量」性质，改动最大 |

**B 的落地要点**：
- Rust 侧：正则 + 括号配对提取 5 条 `GameEntry` 的字段（脆弱但可控；字段少且有固定顺序）。
- mock 侧：提取 `GAME_CATALOG` 数组的 5 个对象字段。
- `hasBundledComponent` 期望值：**读 `data/tools/manifests/*.json` 按 `entry.asset != null` 现算**，
  这样三处口径一次对齐，而不是让 mock 与 Rust 互相「抄答案」。
- 失败时输出可定位的 diff（哪个 id 的哪个字段）。

**建议**：B 先落地；C 作为 Q 项记入 04 §11 待评估（它触及「catalog 是否为编译期静态」的设计决定）。

## 5. P2-5 CI 不跑壳层测试

### 5.1 复核：成立

- `ci.yml` `rust` job（`:121-128`）刻意只跑 4 个领域 crate —— **这个决定是对的**，
  注释给的理由成立（Tauri 在 Linux 需 webkit2gtk 等系统库）。
- `ci.yml` `shell` job（`:162-165`）只有 `cargo check -p orbis`，**不跑 `cargo test`**
  → 壳层 26 个单测在 CI 中从不执行。**P1 正是从这里走脱的。**
- `:163-164` 注释「待 Cargo.lock 提交入库后应改为 `--locked`……锁文件已在本地生成，尚未提交」
  **已过时**：`docs/05` §B6 明确「Cargo.lock **刻意保留入库**（应用需可复现构建）」，
  且近期多次提交都包含 `Cargo.lock`。
- 附带发现：`npm run verify` **不含任何 Rust 闸门**（只有 data / mock / render / arch / typecheck）。

### 5.2 修复方案

`shell` job 在既有 `npm run build` 之后（前端产物已在同 job 内，`generate_context!` 能过）追加：

```yaml
- name: 壳层单元测试（命令接线 / DTO 投影 / 错误映射）
  run: cargo test -p orbis --locked
```

并把 `cargo check -p orbis` 一并改为 `--locked`，同时删掉过时注释。

**顺序要求**：本项与 **P1 的回归测试必须同批落地** —— 否则测试写了也不会在 CI 跑，
等于没修。这是本方案里唯一有硬依赖关系的一对。

（可选）在 `package.json` 增 `test:rust` 脚本，让 `verify` 也能一键覆盖 Rust 侧；
但需权衡 `verify` 的耗时，建议保持 Rust 闸门单独跑。
