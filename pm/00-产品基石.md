## 1. 一句话定义与产品定位

### 1.1 一句话定义

> **一个统一管理二次元 PC 游戏的游戏中心：统一发现、安装、更新、启动、账号、配置，并为每款游戏提供经过版本适配的 PC Enhancement 与专属工具。**

> 注：此为**长期产品定义**。MVP 实际兑现切面见 §5.2 / §5.4——更新仅为只读检测、安装与账号管理不在 MVP、不自研下载引擎。

它不是简单的：

> 「把几个启动器放在一起。」

而是：

> **「把玩家自己的二游 PC 游戏环境统一起来。」**

### 1.2 愿景

让用户不再关心：

- 这个游戏应该去哪个启动器启动？
- 游戏装在哪里？
- 今天哪个游戏有更新？
- 哪个游戏配置坏了？
- 120 FPS 工具现在还能不能用？
- 这个游戏怎么开高级画质？
- 我这个账号到底是哪个？
- 游戏更新后之前的配置怎么办？
- 某个第三方工具到底是否兼容当前版本？

用户只需要打开一个应用：

> **看到自己的游戏 → 选择游戏 → 管理 / 优化 / 启动。**

### 1.3 不是什么

| 不定位为 | 说明 |
|---------|------|
| 二游下载器 | 不是核心目标 |
| HoYoPlay 替代品 | HoYoverse 只是支持对象之一 |
| FPS Unlocker | FPS 解锁只是 Game Tool 的一种 |
| Mod Manager | Mod 可以成为未来能力，但不是产品核心 |
| 单纯聚合启动器 | 「聚合」只是入口 |

### 1.4 是什么

**Anime Game Control Center**

中文暂定：

> **二游 PC 游戏中心**

核心能力：

```
Game Launcher
        +
Game Manager
        +
PC Enhancement
        +
Game Tools
        +
Plugin Platform
```

### 1.5 核心理念

> **游戏是主体，启动器只是入口，工具才是长期价值。**

传统 Launcher：

```
启动游戏
    ↓
结束
```

本产品：

```
发现游戏
   ↓
管理游戏
   ↓
配置游戏
   ↓
增强游戏
   ↓
启动游戏
   ↓
记录状态
   ↓
持续维护
```

### 1.6 价值模型

用户真正需要的不是一个「启动按钮」，而是逐层递进的价值：

| 层级 | 价值 | 说明 |
|------|------|------|
| 第一层 | 方便 | 一个入口管理所有游戏 |
| 第二层 | 省事 | 自动发现、更新、修复、启动 |
| 第三层 | 控制 | 统一分辨率、FPS、启动参数、画质 |
| 第四层 | 增强 | 解决官方客户端没有提供的 PC 能力 |
| 第五层 | 生态 | 不同游戏可以拥有自己的工具 |

```
Launcher
   ↓
Game Manager
   ↓
PC Enhancement
   ↓
Game Tools
   ↓
Plugin Ecosystem
```

### 1.7 North Star

唯一需要长期坚持的核心问题：

> **「玩家打开这个软件之后，是否可以不用再关心其他二游启动器和 PC 游戏工具？」**

如果答案越来越接近「是」，产品就在正确方向上。

### 1.8 内部口号

第一阶段内部定位：

> **One launcher. Every game. Your setup.**

中文：

> **一个入口，管理所有游戏。**

更准确的长期表达：

> **不只是启动游戏，而是管理你的游戏。**

### 1.9 项目性质与开源定位

Orbis 是**开源项目，不做商业化**：

- 不追求商业收入，不设付费墙，能力全部开放
- 核心问题从「为什么用户选」扩展为**「为什么用户和贡献者都选」**
- 护城河叙事转为「不可复制资产」叙事（见 §11）

待决事项：

| 事项 | 状态 |
|------|------|
| 项目自身 License | **已定：GPL-3.0-or-later**（2026-09-18 Phase 0 拍板，证据链见 pm/Phase0-冲刺A-调研记录.md §2） |
| 治理模式 | 待定：个人主导 / 社区共治 |
| 与 Starward / Twintail 关系 | 竞合而非零和，License 允许范围内可借鉴实现、共享适配知识（见 §2.4） |

## 2. 竞品与差异化

最值得参考的不是某一个产品，而是几个不同方向。

### 2.1 Starward

Starward 已经证明：

- 第三方游戏中心存在真实需求
- 用户愿意使用统一入口
- 游戏时间有价值
- 多账号有价值
- 游戏截图有价值
- 抽卡记录有价值

当前定位是 HoYoverse PC 游戏第三方启动器，并支持游戏时间、账号切换、截图、抽卡记录等额外能力。项目目前约 4.5k stars。

**借鉴：**

```
Game Dashboard
Account
Playtime
Game Data
Launcher UX
```

### 2.2 TwintailLauncher

TwintailLauncher 已经进一步验证跨厂商统一管理是可行方向：

```
Genshin
Star Rail
ZZZ
Wuthering Waves
Endfield
PGR
Aether Gazer
...
```

同时覆盖：

- 下载 / 管理 / 启动
- Mod / QoL / Advanced Features
- 下载、更新、修复
- Offline / Weak Network
- 游戏时间
- Discord RPC
- FPS Unlocker
- 环境变量
- Wuthering Waves 特殊适配

技术栈：Tauri / Rust / Web。

说明「Launcher + Tool」实际上已经成为这个生态的重要发展方向。

**借鉴：**

```
跨厂商
Plugin
Download Engine
Game QoL
Tool Integration
```

### 2.3 核心差异化

不是：

> 「我支持更多游戏。」

而是：

> **「我把游戏本身和 PC Enhancement 做成统一的平台。」**

| 能力 | Starward | Twintail | 本产品 |
|------|:--------:|:--------:|:------:|
| HoYo 系 | ✓ | ✓ | ✓ |
| 跨厂商 | △ | ✓ | ✓ |
| 游戏工具 | ✓ | ✓ | ★★★ |
| PC Enhancement | △ | ✓ | ★★★ |
| 工具版本管理 | △ | △ | ★★★ |
| 兼容性系统 | △ | △ | ★★★ |
| 自动回滚 | △ | △ | ★★★ |
| Tool Plugin | △ | ✓ | ★★★ |

这里的表不是给竞品打分，而是明确产品设计重点。

### 2.4 开源竞合策略

开源语境下，竞品同时也是生态：

- **Starward**：HoYo 系深度标杆，其适配知识（检测、游戏时间、抽卡记录）可在 License 允许范围内借鉴
- **TwintailLauncher**：同方向同技术栈（Tauri/Rust），真正的问题是「Orbis 提供了它没有的东西是什么」——答案是 Tool 平台的安全模型（Manifest / 兼容性 / 备份回滚）与开放的 Compatibility 数据集
- 贡献者社区可以重叠，好的架构文档与贡献指南本身就是竞争力

> 差异化主张：不是「支持更多游戏」，而是「让二游 PC 工具变得安全、透明、可维护」。

## 3. 目标用户

### 3.1 Persona A：多二游玩家

同时玩：

- 原神
- 崩坏：星穹铁道
- 绝区零
- 鸣潮
- 终末地

核心需求：

> **一个入口。**

### 3.2 Persona B：PC 性能玩家

关注：

- 120 FPS / 高刷新率
- HDR / DX11 / DX12
- 高级画质 / 超采样 / Ray Tracing
- Borderless

核心需求：

> **游戏 PC 端能力最大化。**

### 3.3 Persona C：折腾型玩家

关注：

- 配置 / Mod / FPS
- 参数 / 游戏文件 / 启动方式

核心需求：

> **不想每个游戏都自己研究一遍。**

## 5. 产品范围与 MVP

### 5.1 首发游戏列表

第一阶段：

```
原神
崩坏：星穹铁道
绝区零
鸣潮
明日方舟：终末地
```

原则：

> **5 款游戏进得来，1 款游戏用得深。**

广度层证明「跨厂商统一入口」（5 款全部可管理），深度层证明差异化价值链（鸣潮 L1 全闭环 + 原神 L3 解锁）。拆解见 §5.2。

### 5.2 MVP 必须完成

MVP 采用**双层结构**：广度层证明跨厂商统一入口，深度层证明差异化价值链。

**游戏范围：** 原神、星铁、绝区零、鸣潮、终末地

**广度层 · P0（5 款全部）：**

- [ ] 自动发现 / 添加游戏 / 删除游戏入口
- [ ] 游戏路径 / 版本
- [ ] 启动 / 停止 / 运行状态
- [ ] 游戏时间
- [ ] 启动参数保存
- [ ] 配置备份 / 配置恢复（范围 = Provider 已声明配置路径的游戏；MVP 确定交付鸣潮，其余随技术设计声明逐个解锁，未声明前显示「暂不支持」）

**深度层 · P0（双标杆：鸣潮 L1 + 原神 L3）：**

鸣潮（L1 · 配置修改，安全模型门面）：

- [ ] 120 FPS Enhancement（LocalStorage.db 配置修改，L1 风险级）
- [ ] 修改前自动备份 / 失败自动回滚
- [ ] 修改后验证
- [ ] Tool 兼容状态展示（游戏更新后未验证状态显式提示）
- [ ] 完整闭环：启用 → 备份 → 修改 → 验证 → 启动 → 更新失效提示 → 一键回滚

原神（L3 · 进程运行时解锁，参考成熟开源项目）：

- [ ] 120 FPS 解锁工具（参考社区成熟开源实现，如 GenshinFPSUnlocker 系 MIT 项目；上游核实为 Phase 0 入场条件，未核实前不锁定实现；**发行包分离**——主安装包不含注入器，首次启用时从项目 Releases 独立资产显式下载并校验哈希）
- [ ] L3 显式风险授权（默认关闭 + 首次启用风险确认 + 用户侧风险披露）
- [ ] 解锁模式启动编排（解锁器随游戏启动自动加载，无需单独操作）
- [ ] 版本兼容门控（游戏更新后未验证即提示并阻止启用）

**P1 砍线（资源紧张时按序顺延）：**

```
1. 绝区零高级启动参数
2. 星铁 120 FPS（复用原神 L3 集成模式，同样有成熟开源参考，顺延至 Phase 3 / V1.x）
3. 终末地 FPS / Graphics（Phase 3 标杆）
4. 诊断中心、配置差异
```

> MVP 的 aha 时刻 = 鸣潮玩家一键启用 120 FPS，游戏更新后被告知「工具尚未验证」，并可一键恢复原配置；原神玩家首次启用解锁时看到完整风险告知，之后每次启动即自动解锁。

### 5.3 MVP PC Enhancement

| 游戏 | 能力 | 层级 |
|------|------|------|
| 鸣潮 | 120 FPS（L1 配置修改） | P0 · 深度标杆 |
| 原神 | 120 FPS 解锁（L3 进程运行时） | P0 · 深度标杆 |
| 星铁 | 120 FPS（L3） | P1 · 顺延至 Phase 3 / V1.x |
| 终末地 | FPS / Graphics | P1 · Phase 3 标杆 |
| 绝区零 | 基础高级启动参数 | P1 |

深度标杆分工（双游戏覆盖风险谱系两端）：

- **鸣潮（L1）**：FPS 修改走配置文件，完整示范备份 / 回滚 / 验证安全模型；官方 PC 端能力弱、社区工具散乱，痛点集中；版本更新频繁，恰好首次验证兼容性系统价值
- **原神（L3）**：有成熟开源项目（MIT 系）可参考，工程成本较低；但反作弊与分发风险仍高，须按 L3 流程披露（默认关闭 + 显式授权 + 发行包分离）；用户基数最大、需求最高频；示范安全模型的另一半——风险披露 + 兼容门控

注意：

> 具体工具是否能够集成，不以「网上存在工具」为充分条件，而以 License、技术稳定性、版本兼容性和风险评估为准。

## 6. 核心能力设计

### 6.1 自动发现

扫描来源：

```
官方 Launcher
常见安装目录
注册表
快捷方式
Steam
Epic
用户手动路径
```

第一版优先：

```
官方 Launcher
常见路径
手动选择
```

### 6.2 更新系统

第一阶段建议：

> **优先调用官方能力 / 官方 Launcher。**

不要第一版就自己重写所有下载协议。

原因：

```
CDN
Patch
Chunk
Preload
Differential Update
Repair
```

这些系统维护成本很高。TwintailLauncher 的近期更新已经可以看出，跨厂商下载、更新、Repair 本身就是一个非常大的工程模块。

**与官方启动器的共存**（需在 MVP 前确认）：

## 8. 安全、信任与合规

### 8.1 Tool 风险分级

必须建立标准。

#### Level 0 — Read Only

例如：

```
游戏版本
游戏路径
游戏时间
硬件信息
配置读取
```

风险：极低。

#### Level 1 — Config

例如：

```
LocalStorage
Graphics Config
Launcher Config
```

特点：修改本地配置文件。

必须：

```
自动备份
修改前验证
修改后验证
失败回滚
```

#### Level 2 — Launch Enhancement

例如：

```
启动参数
窗口模式
DX 参数
环境变量
```

风险：低～中。

#### Level 3 — Process / Runtime

例如：

```
DLL
Hook
Injection
Memory Modification
```

风险：高。

必须明确提示：

> 第三方运行时修改可能与游戏更新、反作弊机制或厂商规则发生冲突。

### 8.2 Tool 权限模型

Tool 安装时明确：

```
读取游戏目录
写入游戏目录
修改配置
管理员权限
进程访问
网络访问
启动外部程序
```

例如：

```
FPS Tool

✓ 读取游戏配置
✓ 修改游戏配置
⚠ 需要管理员权限
⚠ 可能访问游戏进程
```

用户明确授权。

### 8.3 不做隐式操作

严禁：

```
用户点击启动
    ↓
偷偷安装 DLL
    ↓
偷偷修改配置
```

所有高风险操作必须可见。

### 8.4 工具生命周期

```

Validate
   ↓
Backup
   ↓
Apply
   ↓
Verify
   ↓
Use
   ↓
Update
   ↓

```

### 8.6 开源 License 治理

项目本身开源、非商业化，License 治理是工具集成策略的基础。

#### 项目自身 License（已决：GPL-3.0-or-later，2026-09-18 Phase 0 拍板）

决策依据（完整证据链与决策矩阵见 pm/Phase0-冲刺A-调研记录.md §2）：

- Starward（MIT）、FPS Unlocker 全系（MIT）代码在 GPL 下可自由借鉴
- TwintailLauncher 为 **GPL-3.0-only**——仅 GPL 系下可借鉴其代码，选 MIT 即放弃这一借鉴面
- 非商业化定位下 MIT 的商业友好性无实际价值；Compatibility 数据集（§11）需防闭源分叉收割
- AGPL 对桌面应用无增量保护，徒增理解成本

#### 第三方工具 License 记录

原则：

> **GitHub 开源 ≠ 可以随意复制。**

必须记录：

```
Source
Author
Repository
License
Copyright
Redistribution Requirement
Modification Requirement
Notice Requirement
```

尤其：

```
MIT
Apache-2.0
GPL
LGPL
MPL
自定义 License
```

必须分别处理。特别注意 GPL 系传染性：GPL 工具可作为外部进程调用；若嵌入或静态链接其代码，须重新评估集成方式与项目自身 License 的兼容性。

例如现有 Genshin/Star Rail FPS 项目中就可以看到 MIT License；而不同项目的具体授权条件仍然需要逐项核对。

#### 贡献治理（待定）

贡献指南、行为准则；CLA 可选。

## 11. 护城河与长期资产

### 11.1 不可复制资产

「支持 5 个游戏」可以被模仿，代码可以被 fork。开源语境下，真正的长期护城河应理解为**不可复制资产**：

| # | 护城河 | 说明 |
|---|--------|------|
| 1 | Game Adapter | 知道不同游戏怎么工作 |
| 2 | Tool Ecosystem | 拥有大量高质量工具 |
| 3 | Compatibility Database | 知道什么版本能用什么工具 |
| 4 | Backup / Rollback | 让用户敢用 |
| 5 | UX | 让复杂的东西看起来简单 |

### 11.2 最核心的数据资产

长期来看最有价值的不是用户数量本身，而是：

```
Game
Version
Tool
Compatibility
Configuration
```

形成：

```
Game Version Graph
```

例如：

```
Genshin 6.0
 ├─ FPS 1.3 ✓
 ├─ Graphics 2.0 ✓
 └─ Tool X ✕

Genshin 6.1
 ├─ FPS 1.4 ✓
 ├─ Graphics 2.1 ?
 └─ Tool X ✕
```

这会成为产品的重要基础设施。

Compatibility DB 定义为**开放数据集**：社区共建、可导出、可校验。

#### 数据生产机制（冷启动解法）

冷启动悖论（无用户 → 无数据 → 无差异化 → 无用户）必须用生产机制而非规模解决：

```
自动化验证流水线（长期目标）：游戏更新 → 自动拉取 → 沙箱测试 → 写回
社区共建：用户提交本地验证结果（附证据）
版本更新后人工复验：优先标杆游戏
```

## 12. 原则、规则与验收

### 12.1 第一版产品原则

| # | 原则 | 说明 |
|---|------|------|
| 01 | **快** | 打开 → 游戏 → 启动 |
| 02 | **稳** | 工具失败不能拖垮游戏 |
| 03 | **透明** | 所有修改可见 |
| 04 | **可恢复** | 任何修改都有 Backup / Rollback |
| 05 | **版本感知** | 任何 Tool 都必须知道自己对应哪个游戏版本 |
| 06 | **插件化** | 新增游戏 ≠ 修改 Core |

### 12.2 UX 原则

用户不应该知道：

```
LocalStorage.db
SQLite
DLL
Hook
Registry
Signature
Patch
```

用户只需要看到：

```
120 FPS
高级画质
配置备份
一键恢复
```

也就是说：

> **复杂度应该隐藏在 Core，简单度应该呈现在 UI。**

但高级用户必须能够看到底层：

```
Advanced

Modified:
LocalStorage.db

Changed:
KeyCustomFrameRate

Old:
60

New:
120
```

产品同时满足：

```
普通用户：简单
高级用户：透明
开发者：可扩展
```

### 12.3 开发团队必须遵守的 10 条规则

1. Game Core 不允许硬编码具体游戏逻辑。
2. 所有游戏通过 Game Provider 接入。
3. 所有增强功能通过 Tool Provider 接入。
4. Tool 必须有版本和兼容性。
5. 修改配置前必须 Backup。
6. 修改失败必须能够 Rollback。
7. 高风险操作必须显式授权。
8. 第三方开源项目必须记录 License / Source / Author。
9. Launcher 本身不能依赖任何单一 Tool。
10. UI 不应该暴露底层复杂性，但高级模式必须允许用户检查。

### 12.4 MVP 验收清单

**A · MVP 功能验收**（发布门槛）：

```
—— 广度层 ——
[ ] 能自动发现 5 款游戏
[ ] 能正确识别安装路径 / 版本
[ ] 能直接启动并检测运行状态
[ ] 能记录游戏时间
[ ] 能保存启动参数
[ ] 能创建配置备份 / 恢复配置
—— 深度层（鸣潮 L1）——
[ ] 能安装 / 启用 120 FPS Enhancement
[ ] Tool 修改前自动备份
[ ] Tool 修改失败自动回滚
—— 深度层（原神 L3）——
[ ] 解锁工具默认关闭，首次启用有显式风险确认
[ ] 解锁模式启动原神，游戏内 120 FPS 生效
—— 深度层通用 ——
[ ] 能显示 Tool 兼容状态
[ ] 游戏更新后未验证状态显式提示
—— 通用 ——
[ ] Tool 失败不会影响 Launcher
[ ] 所有高风险操作有明确提示
[ ] 有统一日志
```

**B · 架构不变量**（非一次性发布门槛，以自动化测试持续保障）：

```
[ ] 新增游戏不需要修改 Core
[ ] 新增 Tool 不需要修改 Core
```

诊断信息降级为 P1，不作发布门槛。

### 12.5 当前项目一句话总结

> **做一个面向二次元 PC 游戏玩家的统一 Game Control Center，以启动、更新、账号和游戏管理为基础，以 FPS / 画质 / 启动参数等 PC Enhancement 为差异化，以 Game Plugin + Tool Plugin 为扩展机制，并通过版本兼容、备份回滚和透明权限体系，让第三方游戏工具变得简单、可靠、可维护。**

> 注：此为长期形态总结。MVP 兑现切面：启动 / 管理 / 双标杆增强（鸣潮 L1 + 原神 L3）+ 只读更新检测；账号与自研下载不在 MVP（§5.2 / §5.4）。

## 14. 术语表

| 术语 | 含义 |
|------|------|
| **Orbis** | 项目代号；产品正式名待定 |
| **Game Control Center** | 产品类型定位：游戏控制中心，而非单纯启动器 |
| **Game Provider** | 某一款游戏的接入适配器，负责发现/启动/更新/配置 |
| **Tool / Tool Plugin** | 挂在某游戏下的增强能力单元（FPS、画质、启动参数等） |
| **Tool Manifest** | Tool 的描述文件：版本、兼容性、风险、权限 |
| **PC Enhancement** | 面向 PC 端的画质/帧率/显示等增强能力层 |
| **Compatibility Database** | 游戏版本 × 工具版本的兼容状态库（长期资产） |
| **Backup / Rollback** | 修改前备份、失败自动回滚 |
| **Launch Profile** | 一组可切换的启动配置（分辨率/帧率/窗口等） |
| **Risk Level** | Tool 风险分级 L0–L3（只读 → 配置 → 启动增强 → 进程级） |
| **North Star** | 长期核心判断问题：打开本软件后是否不再需要其他二游工具 |
