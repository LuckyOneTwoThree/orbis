### 1.3 刻意不做（防过度设计）

- **动态插件加载**：MVP 工具全部内置，Manifest 是数据声明而非热加载机制（`orbis-builtin/*` / `orbis-bundled/*` 命名空间已预留外部化，P0-C §1.2）
- **应用自更新**：MVP 不做，GitHub Releases 手动下载
- **i18n 框架**：MVP 中文单语；文案集中管理 + 轻量 `t()` 封装，框架 P1+
- **诊断中心 / 配置差异**：P1（01 §4）
- **下载引擎 / 账号 / 云同步**：不做（01 §4）

| 打包 | Tauri bundler（NSIS 优先） | R4 无签名兜底 = 白名单引导文档（02 §6） |

### 2.2 依赖治理（00 §8.6 义务）

- 核心依赖均为宽松许可（MIT / Apache-2.0 / BSD 系），**不与项目自身的 GPL-3.0-or-later 冲突**——依赖方向是「宽松许可代码进入 GPL 项目」，该方向无传染问题（P0-A §2 决策面不受影响）
- 反向约束才是红线：**GPL 系工具只作外部进程调用，不嵌入、不静态链接**（00 §8.6），否则会改变项目自身许可义务的适用边界
- CI 引入 `cargo deny check`（License 白名单 + 重复依赖 + 安全公告）
- 发布 checklist 含 NOTICE 文件生成（第三方组件 + 上游工具声明，02 §5「开源合规」行）；F4 上游为 MIT，须在 NOTICE 中逐项署名

## 3. 进程与运行时架构

### 3.1 进程拓扑

```
┌───────────────────────────────── Windows ─────────────────────────────────┐
│                                                                            │
│  ┌────────────────┐    Tauri IPC     ┌─────────────────────────────────┐  │
│  │  WebView (UI)  │◄────────────────►│  Orbis 主进程（Rust Core）       │  │
│  │  React + TS    │   命令 + 事件    │  Workspace crates 组装           │  │
│  │  S0–S6 页面    │                  │  默认普通用户权限（00 §8.9）     │  │
│  └────────────────┘                  └────────┬───────────────┬────────┘  │
│                                               │ spawn         │ spawn    │
│                                     ┌─────────▼──────┐ ┌─────▼─────────┐ │
│                                     │ 游戏进程        │ │ 解锁器子进程   │ │
│                                     │（5 款游戏 exe）│ │（B7 独立资产） │ │
│                                     └────────────────┘ └───────────────┘ │
│                                                                            │
│   出网（只读 / 低频 / 用户可关，P0-B §5.4）：                                │
│   HoYoPlay API · 库洛 CDN index.json · GitHub Releases（解锁器资产）        │
└────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 职责边界

| 进程 | 职责 | 禁止 |
|------|------|------|
| WebView UI | 呈现 + 交互意图表达（S0–S6，03 §3） | 不接触路径拼接 / SQL / 进程句柄 / 哈希（00 §7.9） |
| Orbis 主进程 | 全部决策：扫描、版本比对、门控、备份、写入、编排、日志 | 不依赖任何单一 Tool 存活（00 原则 02） |
| 解锁器子进程 | 原神运行时解锁（上游 CLI 模式） | 无 UI 依赖；退出不拖垮主进程 |
| 游戏进程 | 不感知 Orbis | Orbis 不注入非 L3 授权进程 |

### 3.3 权限模型

- **Orbis 主进程默认普通用户权限运行**（00 §8.9），不申请永久管理员
- **解锁器子进程的提权需求待 T4 裁决**（P0-A §1.2：上游以管理员权限运行并拉起游戏进程）——若确认每次启动需提权，per-launch UAC 弹窗与 02 B8「无需任何额外手动操作」验收直接冲突，须回编排层重新设计（候选出路见 §5.9 方案 A / §11 Q6）
- 写入目标权限不足（如鸣潮装于 `Program Files`）→ precheck 失败 → 阻止 + 引导（§7.1）；受限提权方案为开放问题（§11 Q2）

## 4. 代码架构：Workspace 与分层

### 4.1 Workspace 与依赖方向

```
orbis/
├── pm/                              # 产品文档（既有，00–04）
├── docs/                            # 工程文档：ipc-contract.md（契约单源）/ 实测-T1-T7.md / 05-开工前置清单
├── data/
│   ├── compatibility/seed.json      # 兼容性种子表（P0-C §4.1）+ seed.schema.json
│   └── tools/
│       ├── manifests/*.json         # 内置工具 Manifest（C1）+ manifests.schema.json
│       └── assets.json              # 解锁器发行资产清单（URL + SHA256，B7）+ assets.schema.json
├── crates/
│   ├── orbis-core/                  # 领域模型 + 能力 trait + 兼容引擎（零游戏知识）
│   ├── orbis-platform/              # SQLite / 进程 / 注册表 / 日志 / 备份（OS 落地）
│   ├── orbis-providers/             # 5 游戏装配 + 3 版本 adapter + 鸣潮 ConfigProvider + 扫描规则
│   └── orbis-tools/                 # Manifest 加载 + L1/L3 执行器 + 解锁器资产
├── src-tauri/                       # Tauri 壳：命令注册 / 生命周期 / 事件桥（唯一组装点）
└── src/                             # React UI（S0–S6）
    └── api/                         # 契约层：ui 只依赖 OrbisApi 接口，不直接 invoke
```

依赖规则（编译期保证架构不变量，详见 §9.1）：

```
providers → core, platform
tools     → core, platform
platform  → core
src-tauri → providers, tools, platform, core      （唯一允许依赖全部的组装根）
禁止：providers ↔ tools 横向依赖；core 依赖任何上游 crate
```

### 4.2 GameProvider 装配模型（两级结构）

00 §7.2 的完整 `GameProvider`（install/update/repair/account）是长期形态；MVP 按 P0-B §5 拆为**按能力横切的 trait** + **每游戏一个装配条目**：

```rust
// orbis-core —— 能力 trait（签名级伪代码）

pub trait VersionSource: Send + Sync {
    /// region 从第一天进入签名（P0-B §5.1，Q7）
    async fn remote_version(&self, game: GameId, region: Region)
        -> Result<RemoteVersion, VersionError>;
}

pub trait ConfigSource: Send + Sync {
    /// A8 范围依据：声明式备份范围（未声明 = UI「暂不支持备份」）
    fn declared_paths(&self, install: &GameInstallation) -> Vec<PathBuf>;
    /// 前置检查：进程未运行 + 写权限（P0-B §6.3 红线 1）
    fn precheck(&self, install: &GameInstallation) -> Result<(), PrecheckError>;
    fn read_keys(&self, install: &GameInstallation, keys: &[ConfigKey])
        -> Result<Vec<ConfigValue>, ConfigError>;
    /// 幂等 upsert 写入（§5.3）
    fn apply(&self, install: &GameInstallation, plan: &[ConfigChange]) -> Result<(), ConfigError>;
}

pub trait LaunchSpec: Send + Sync {
    fn executable(&self, install: &GameInstallation) -> PathBuf;
    fn default_args(&self, region: Region) -> Vec<String>;   // 待实测 T5
}

pub trait DetectRule: Send + Sync {
    fn detect(&self) -> Vec<GameInstallationCandidate>;       // 只读，L0
}

/// 装配根：每个游戏一个条目（00 §7.1「每个游戏都是一个 Provider」）
pub struct GameProvider {
    pub game: GameStaticInfo,                    // id / name / publisher / icon
    pub detect: Box<dyn DetectRule>,
    pub version: Option<Box<dyn VersionSource>>, // None = 降级展示
    pub config: Option<Box<dyn ConfigSource>>,   // None = 「暂不支持备份」（A8）
    pub launch: Box<dyn LaunchSpec>,
}
```

MVP 装配表（5 款）：

| GameId（P0-C §1.2 slug） | VersionSource | ConfigSource | 状态说明 |
|--------------------------|---------------|--------------|----------|
| `genshin-impact` | `HoyoPlayAdapter` | —（L3 不落盘，A8 不适用） | E1 直连 |
| `honkai-star-rail` | `HoyoPlayAdapter` | — | E1 直连 |
| `zenless-zone-zero` | `HoyoPlayAdapter` | — | E1 直连 |
| `wuthering-waves` | `KuroAdapter` | `WuwaConfigProvider` | L1 深度标杆 |
| `arknights-endfield` | `DegradedAdapter` | — | E1 降级（P0-B §3） |

`Region = { Cn, Global, Bili }`（Q7；Bili 版本内容随国服，版本源复用 Cn）。库内序列化值统一为小写 `cn | global | bili`（前端同名字面量，禁止出现「国服」「技术测试」这类展示文案入库）。

**与 00 §7.2 的关系（避免实现者误解）**：00 §7.2 的完整 `GameProvider`（`install` / `uninstall` / `update` / `repair` / `getConfig` / `backupConfig` / `restoreConfig`）是**长期形态**，其中 `install` / `uninstall` / `update` / `repair` 在 MVP **一律不实现**（01 §4 明确不做；E 域只做只读检测）。MVP 落地的是上表 5 个 trait 的**能力子集**：发现（`DetectRule`）、版本读取（`VersionSource`）、配置读写与备份（`ConfigSource`）、启动（`LaunchSpec`）。新增游戏只需补 providers 模块 + catalog 条目 + seed 数据，不需要触碰 Core（架构不变量 B1 / §9.1）。

## 5. 核心模块设计

### 5.1 GameScanner（A1 / A2 / A3）

**发现规则（每游戏 `DetectRule`，严格只读）：**

| 游戏 | 规则来源 |
|------|----------|

**校验与识别：**

- 候选必须通过 exe 文件特征校验（防「官方启动器当游戏本体」，02 A2 边界）
- 本地版本识别顺序：exe `VERSIONINFO` → 特征文件 / 目录名 → `Unknown`（不猜、不显示过期缓存，02 A3）；识别方式记入 `version_source`
- **版本归一化契约**：`VERSIONINFO` 实际产出常为多段构建号（如 `7.0.10.xxxxx`），而种子表与版本源口径为 `major.minor`——识别产出为**原始值**，一律先经 `normalize(raw) -> (major, minor)`（取前两段数值；任一段缺失 / 非数值 → 按 `Unknown` 处理，不猜）再消费。原始值与归一化值分列存储（§6.1 `local_version` / `version_norm`），种子查询（§5.6）与 E1 比较（§5.2）**只消费归一化值**
- 扫描超时 / 权限不足 → 部分结果 + 手动添加引导，不阻塞启动（02 A1）

### 5.5 EnhancementExecutor：L1 链路状态机（B1–B4）

```
enableTool(wuwa-fps-120)
   │
   ▼
[Gate] 兼容门控（分层，00 §4.4 / P0-C §2.1）：
       Verified / Compatible → 通过
       Unknown · L1 工具   → 拦截 + 显式提示 + 「继续使用」覆盖入口（覆盖动作写日志）
       Unknown · L3 工具   → 硬阻止（02 B7「拦截并阻止」）
       Incompatible / Deprecated → 一律硬阻止 + 原因（B6）
   │
   ▼
[Precheck] 进程 / 写权限（红线 1）
   │
   ▼
[Backup] BackupManager::create(PreModify)     —— B2：无备份不修改（硬性顺序）
   │
   ▼
[Modify] ConfigSource::apply（双键 = 120）      —— B1
   │
   ▼
[Verify] read_back(双键) == 期望                —— B3
   │                    │
   ok                   fail
   │                    ▼
[Applied]          [RollingBack] restore(最新备份) + 哈希校验 —— B4
   │                    │
   ▼                    ▼
收尾事件 + 日志      [RolledBack] 明示「修改失败，已自动恢复原配置」
```

- 状态枚举：`Pending → GatePassed → BackedUp → Modified → Verified | RollingBack → RolledBack`
- Unknown 覆盖（仅 L1）入口位于 S2a Enhancement 卡片，交互规格随 03 下轮对齐补充；覆盖执行同样走完整备份 → 修改 → 验证链路——不因用户选择继续而跳过安全模型
- **每步** = 一次 `tool:apply-step` 事件（驱动 D4 透明卡片）+ 一条结构化日志（00 §9.1，Category = Backup / Modify / Verify / Rollback）
- 执行器内 `catch_unwind`：工具链路任何 panic 转入 RollingBack，**不影响主进程**（00 原则 02 / 12.4 A「Tool 失败不影响 Launcher」）

### 5.8 UnlockerRunner（B7，L3，发行包分离）

**首次启用流程（P0-A §1.3 口径）：**

### 5.12 应用级约束与并发保护

开工前审计补入（docs/05 §4）。前 11 节都是「功能模块」，本节约束的是**进程与应用级不变量**——没有它，前 11 节的安全设计在并发与异常路径下会被绕过。

| 约束 | 机制 | 为什么必须有 |
|------|------|--------------|
| **单实例互斥** | 进程启动时抢占命名互斥量（或 `tauri-plugin-single-instance`）；第二个实例不启动 Core，仅把已有窗口前置并退出 | 两个 Core 并存会并发写同一 `LocalStorage.db`、重复计数游戏时长、并各自持有备份目录视图——`installation.executable_path UNIQUE` 也挡不住这种破坏 |
| **按安装实例串行化** | Core 内 `per-installation` 写锁（内存 Mutex）；同一 `installation_id` 上的 modify / backup / restore 互斥排队 | 防 UI 双击、事件重入、多页面并发触发导致的「备份 → 修改 → 修改」交错，破坏 §5.5 的硬性顺序约束 |
| **备份前空间检查** | `create` 第一步估算所需字节（源目录大小）并检查剩余空间 ≥ 需求 × 1.5；不足则返回 `BACKUP_SPACE_INSUFFICIENT` 并**阻止进入 Modify** | 磁盘写满会让备份半途失败，若此时已进入 Modify 就意味着「改了但没备份」，直接违反 00 §12.3 规则 5 |
| **降级必须落日志并可回读** | 任何被约束拦下的操作（空间不足 / 已在运行 / 兼容门控）都要写 D3 日志并在 UI 显式呈现（§8 总原则） | 禁止静默失败 |

> UI 侧不承担并发正确性——UI 可以只靠禁用按钮提升体验，但**正确性必须由 Core 的锁与顺序保证**（00 §7.9：UI 只表达交互意图）。

### 6.4 状态模型定稿（两维 + 正交标志）

**问题**：00 §5.7 把 7 个游戏状态并列列出（`Installed / Running / Updating / Repairing / Broken / UpdateAvailable / Unknown`），但它们在语义上**不是同一维度**——`UpdateAvailable` / `Unknown` 与 `Installed` / `Running` 可以同时成立（「已安装且可更新」「已安装但版本未知」）。若实现为单一互斥枚举，就会出现「有更新就显示不出运行中」这类表达力丢失，首页「需处理」也无法正确聚合。本节把 00 §5.7 的意图**精确化**（不推翻：00 的 7 个标签仍是 UI 可见状态集合，只是内部建模拆为三层）。

#### 6.4.1 内部模型三层

```
① 互斥主状态  GameRuntimeStatus = installed | running | updating | repairing | broken
                 └ MVP 实际只会出现 installed / running / broken（updating / repairing 属 P1 更新执行，见 01 §4）
② 正交标志    updateAvailable : bool     （E1 派生：version_norm < remote_version_norm）
              versionUnknown  : bool     （A3 派生：local_version 为 NULL 或 normalize 失败）
③ 工具维      ToolCompatStatus = verified | compatible | unknown | incompatible | deprecated   （§5.6，权威 = seed.json）
              + toolEnabled : bool       （C2）
              + assetState  : not_required | missing | ready | hash_mismatch  （B7 专用）
```

- ①②存入 `installation`（`status` / `local_version`+`version_norm` 派生）；③存在 `tool_state` + 内存中的 seed 索引
- `versionUnknown` **不可省略**：02 A3 要求「识别失败必须显式可见」，若只靠 `local_version = NULL` 隐式表达，UI 会漏提示
- 远程版本不落库（00 §7.10 `GameVersion` 实时探测不入库），因此 `updateAvailable` 是**会话内派生值**，由 `version:refreshed` 事件推给 UI

#### 6.4.2 UI 组合规则（映射 03 §2.2 状态语义）

主标签（pill 只显示**一个**，取优先级最高者）：

| 优先级 | 条件 | 呈现 | 颜色（03 §2.2） |
|--------|------|------|-----------------|
| 1 | `status == running` | 运行中（发光圆点） | 青 |
| 2 | `status == broken` | 异常 | 红 |
| 3 | `status ∈ {updating, repairing}` | 更新中 / 修复中 | 青 |
| 4 | `updateAvailable` | 可更新（描边胶囊） | 粉紫 |
| 5 | 其余 | 已就绪 | 青 |

附加标注（与主标签并列，不抢占主位）：

- `versionUnknown` → 名称旁「版本未知」弱化小字（不可点击、不可隐藏，02 A3）
- 工具维**独立成 pill**（不与游戏态合并）：`verified/compatible` → 青对勾；`unknown` → 粉紫问号 + 行动建议；`incompatible/deprecated` → 红 + 阻止说明

#### 6.4.3 「需处理」聚合定义（D1 验收的判定式）

```
needsAttention(installation) :=
      updateAvailable                     // 有更新（可能让工具失效，02 E1）
   ∨  status == broken                    // 游戏异常
   ∨  versionUnknown                      // 版本无法识别（B6 / E1 的判定基础缺失）
   ∨  ∃ tool ∈ tools(gameId):
          tool.compat ∈ { unknown, incompatible, deprecated }
          // 不论工具是否启用——用户需要知道「这个工具现在还能不能用」正是 00 §8.8 的价值主张；
          // 鸣潮 live 3.x = Unknown 将常态命中，符合 P0-C §3.1「MVP 首个 Unknown 展示案例」
```

- 首页摘要条文案 = 命中数 + 分类计数（「N 个游戏需要处理 · M 个更新可用」），由该判定式驱动，**UI 侧只消费结果不重算**（§3.2：主进程承担全部决策）
- 该判定式同时是 `getUpdateStatus` / `listInstallations` 返回结构的一部分，避免 UI 与 Core 各判一次

## 7. 安全模型落地（L0–L3）

### 7.1 L1（鸣潮 120 FPS）执行红线汇总

P0-B §6.3 五条红线全部映射到机制（§5.3 表）；补充两条 UI 义务：

- **启用成功提示**：「游戏内修改画质会将帧率锁回 60，需重新启用工具」（红线 2 的文案义务）
- **Advanced 视图**（00 §12.2）：透明卡片可展开底层细节 —— `Modified: LocalStorage.db · Changed: KeyCustomFrameRate · Old: 60 → New: 120`

### 7.2 L3（原神解锁）授权与门控

| 环节 | 机制 |
|------|------|
| 默认状态 | `enabled = false`（C3 验收） |
| 首次启用 | 版本化风险文案（进程级修改说明 / 社区历史情况 / 不承诺绝对安全，02 B7）→ 显式勾选 → `authorization_json` 记录文案哈希与时间 |
| 持续门控 | 每次启动编排重新查询 seed（版本更新 → Unknown → 阻止 + 行动建议） |
| 资产完整性 | SHA256 双重校验（下载时 + 每次加载时） |
| 失败降级 | 解锁器任何失败 → 普通启动 + 「本次未解锁」（§5.8） |
| 风险口径 | 「社区多年实践、非官方授权」统一文案（P0-B §6.4） |

### 7.3 L0 / L2 边界（MVP 内不涉新机制）

- L0（扫描 / 版本 / 时长）：严格只读，不碰进程内存（02 A1 边界）
- L2（启动参数 A7）：参数持久化 + 实际生效，MVP 不做参数冲突检测（02 A7 边界）

### 7.4 安全模型不可被用户关闭（设置项边界）

开工前审计补入（docs/05）。设置页与任何开关**不得提供关闭安全模型的入口**：

| 允许作为设置项 | 必须恒为开启（不可作为开关暴露） |
|----------------|----------------------------------|
| `version_check.enabled`（E1 只读探测，02 E1「用户可关」） | 修改前强制备份（00 §12.3 规则 5） |
| `log.retention_days`（Q4） | 修改后验证 + 失败自动回滚（规则 6） |
| `playtime.checkpoint_sec`（A6） | L3 显式授权门槛（规则 7 / C3） |
| — | 兼容门控（B6） |

> 设置页**只允许出现 §6.1 预置键**。新增设置项必须先回 01 清单评审（继承 01 §1），不允许在 UI 阶段先加开关再补后端——「启动后最小化至托盘」等行为项属 D5 待定范围（01 F3），未定稿前不出现在界面上。

> 例外说明：唯一可「绕过」的是 **L1 工具在 `Unknown` 状态下的「继续使用」覆盖**（§5.5），但那是**逐次、显式、留痕**的覆盖，且覆盖后仍走完整「备份 → 修改 → 验证」链路——不是把机制关掉。UI 文案应写成「本次继续使用」而非「不再提示」。

## 8. 降级与错误策略

| 场景 | 行为 | 依据 |
|------|------|------|
| 版本源不可达 / 超时 | `Unknown`，不误报 | 02 E1 验收 |
| 终末地 E1 | 本地版本展示 + 官方渠道引导，标「调研中」 | P0-B §3.2 |
| 种子表缺失 / 损坏 | 兼容查询全部 `Unknown` | 02 C4 验收 |
| 单个 Manifest 损坏 | 该工具不可见，其余正常 | 02 C1 验收 |
| 解锁器下载 / 加载失败 | 阻止启用或降级普通启动 + 明示 | 02 B7 边界 |
| 写权限不足 | precheck 阻止 + 引导 | 02 A8 / B1 |
| 备份失败 | 不进入 Modify（顺序约束） | 02 B2 |
| 工具链路 panic | catch_unwind → 回滚 → 主流程不受影响 | 00 原则 02 |
| 扫描超时 / 权限不足 | 部分结果 + 手动添加引导 | 02 A1 |
| 版本无法识别 | `Unknown`，不显示过期缓存 | 02 A3 |

**总原则：任何降级必须显式可见，禁止静默失败（00 §8.3 不做隐式操作）。**
