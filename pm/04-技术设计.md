## 3. 进程与运行时架构

### 3.1 进程拓扑

```
┌───────────────────────────────── Windows ─────────────────────────────────┐
│                                                                            │
│  ┌────────────────┐    Tauri IPC     ┌─────────────────────────────────┐  │
│  │  WebView (UI)  │◄────────────────►│  Orbis 主进程（Rust Core）       │  │
│  │  React + TS    │   命令 + 事件    │  Workspace crates 组装           │  │
│  │  S0–S6 页面    │                  │  默认普通用户权限（00 §8.9）     │  │
│  └────────────────┘                  └────────┬───────────────┬────────┘  │
│                                               │ spawn         │ spawn    │
│                                     ┌─────────▼──────┐ ┌─────▼─────────┐ │
│                                     │ 游戏进程        │ │ 解锁器子进程   │ │
│                                     │（5 款游戏 exe）│ │（B7 独立资产） │ │
│                                     └────────────────┘ └───────────────┘ │
│                                                                            │
│   出网（只读 / 低频 / 用户可关，P0-B §5.4）：                                │
│   HoYoPlay API · 库洛 CDN index.json · GitHub Releases（解锁器资产）        │
└────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 职责边界

| 进程 | 职责 | 禁止 |
|------|------|------|
| WebView UI | 呈现 + 交互意图表达（S0–S6，03 §3） | 不接触路径拼接 / SQL / 进程句柄 / 哈希（00 §7.9） |
| Orbis 主进程 | 全部决策：扫描、版本比对、门控、备份、写入、编排、日志 | 不依赖任何单一 Tool 存活（00 原则 02） |
| 解锁器子进程 | 原神运行时解锁（上游 CLI 模式） | 无 UI 依赖；退出不拖垮主进程 |
| 游戏进程 | 不感知 Orbis | Orbis 不注入非 L3 授权进程 |

### 3.3 权限模型

- **Orbis 主进程默认普通用户权限运行**（00 §8.9），不申请永久管理员
- **解锁器子进程的提权需求待 T4 裁决**（P0-A §1.2：上游以管理员权限运行并拉起游戏进程）——若确认每次启动需提权，per-launch UAC 弹窗与 02 B8「无需任何额外手动操作」验收直接冲突，须回编排层重新设计（候选出路见 §5.9 方案 A / §11 Q6）
- 写入目标权限不足（如鸣潮装于 `Program Files`）→ precheck 失败 → 阻止 + 引导（§7.1）；受限提权方案为开放问题（§11 Q2）

## 4. 代码架构：Workspace 与分层

### 4.1 Workspace 与依赖方向

```
orbis/
├── pm/                              # 产品文档（既有）
├── data/
│   ├── compatibility/seed.json      # 兼容性种子表（P0-C §4.1）
│   └── tools/
│       ├── manifests/*.json         # 内置工具 Manifest（C1）
│       └── assets.json              # 解锁器发行资产清单（URL + SHA256，B7）

│   ├── orbis-core/                  # 领域模型 + 能力 trait + 兼容引擎（零游戏知识）
│   ├── orbis-platform/              # SQLite / 进程 / 注册表 / 日志 / 备份（OS 落地）
│   ├── orbis-providers/             # 5 游戏装配 + 3 版本 adapter + 鸣潮 ConfigProvider + 扫描规则
│   └── orbis-tools/                 # Manifest 加载 + L1/L3 执行器 + 解锁器资产
├── src-tauri/                       # Tauri 壳：命令注册 / 生命周期 / 事件桥（唯一组装点）
└── src/                             # React UI（S0–S6）
```

依赖规则（编译期保证架构不变量，详见 §9.1）：

```
providers → core, platform
tools     → core, platform
platform  → core
src-tauri → providers, tools, platform, core      （唯一允许依赖全部的组装根）
禁止：providers ↔ tools 横向依赖；core 依赖任何上游 crate
```

### 4.2 GameProvider 装配模型（两级结构）

00 §7.2 的完整 `GameProvider`（install/update/repair/account）是长期形态；MVP 按 P0-B §5 拆为**按能力横切的 trait** + **每游戏一个装配条目**：

```rust
// orbis-core —— 能力 trait（签名级伪代码）

pub trait VersionSource: Send + Sync {
    /// region 从第一天进入签名（P0-B §5.1，Q7）
    async fn remote_version(&self, game: GameId, region: Region)
        -> Result<RemoteVersion, VersionError>;
}

pub trait ConfigSource: Send + Sync {
    /// A8 范围依据：声明式备份范围（未声明 = UI「暂不支持备份」）
    fn declared_paths(&self, install: &GameInstallation) -> Vec<PathBuf>;
    /// 前置检查：进程未运行 + 写权限（P0-B §6.3 红线 1）
    fn precheck(&self, install: &GameInstallation) -> Result<(), PrecheckError>;
    fn read_keys(&self, install: &GameInstallation, keys: &[ConfigKey])
        -> Result<Vec<ConfigValue>, ConfigError>;
    /// 幂等 upsert 写入（§5.3）
    fn apply(&self, install: &GameInstallation, plan: &[ConfigChange]) -> Result<(), ConfigError>;
}

pub trait LaunchSpec: Send + Sync {
    fn executable(&self, install: &GameInstallation) -> PathBuf;
    fn default_args(&self, region: Region) -> Vec<String>;   // 待实测 T5
}

pub trait DetectRule: Send + Sync {
    fn detect(&self) -> Vec<GameInstallationCandidate>;       // 只读，L0
}

/// 装配根：每个游戏一个条目（00 §7.1「每个游戏都是一个 Provider」）
pub struct GameProvider {
    pub game: GameStaticInfo,                    // id / name / publisher / icon
    pub detect: Box<dyn DetectRule>,
    pub version: Option<Box<dyn VersionSource>>, // None = 降级展示
    pub config: Option<Box<dyn ConfigSource>>,   // None = 「暂不支持备份」（A8）
    pub launch: Box<dyn LaunchSpec>,
}
```

MVP 装配表（5 款）：

| GameId（P0-C §1.2 slug） | VersionSource | ConfigSource | 状态说明 |
|--------------------------|---------------|--------------|----------|
| `genshin-impact` | `HoyoPlayAdapter` | —（L3 不落盘，A8 不适用） | E1 直连 |
| `honkai-star-rail` | `HoyoPlayAdapter` | — | E1 直连 |
| `zenless-zone-zero` | `HoyoPlayAdapter` | — | E1 直连 |
| `wuthering-waves` | `KuroAdapter` | `WuwaConfigProvider` | L1 深度标杆 |
| `arknights-endfield` | `DegradedAdapter` | — | E1 降级（P0-B §3） |

`Region = { Cn, Global, Bili }`（Q7；Bili 版本内容随国服，版本源复用 Cn）。

## 5. 核心模块设计

### 5.1 GameScanner（A1 / A2 / A3）

**发现规则（每游戏 `DetectRule`，严格只读）：**

| 游戏 | 规则来源 |
|------|----------|
| 米哈游系 ×3 | 注册表安装键（键名清单随 T7 实测定稿）+ 常见路径 + `getGameConfigs` 的 `installation_dir` 在线提示（可选辅助，P0-B §1.1） |
| 鸣潮 | `%APPDATA%\KRLauncher\*\*\kr_starter_game.json` 的 `path` 字段（P0-B §6.1）+ 常见路径 |
| 终末地 | `C:\Program Files\GRYPHLINK\` 布局 + 常见路径 |
| 兜底 | 各盘符标准目录探测（**不做全盘扫描**，NFR ≤ 3s，02 §5） |

**校验与识别：**

- 候选必须通过 exe 文件特征校验（防「官方启动器当游戏本体」，02 A2 边界）
- 本地版本识别顺序：exe `VERSIONINFO` → 特征文件 / 目录名 → `Unknown`（不猜、不显示过期缓存，02 A3）；识别方式记入 `version_source`
- **版本归一化契约**：`VERSIONINFO` 实际产出常为多段构建号（如 `7.0.10.xxxxx`），而种子表与版本源口径为 `major.minor`——识别产出为**原始值**，一律先经 `normalize(raw) -> (major, minor)`（取前两段数值；任一段缺失 / 非数值 → 按 `Unknown` 处理，不猜）再消费。原始值与归一化值分列存储（§6.1 `local_version` / `version_norm`），种子查询（§5.6）与 E1 比较（§5.2）**只消费归一化值**
- 扫描超时 / 权限不足 → 部分结果 + 手动添加引导，不阻塞启动（02 A1）

### 5.2 VersionProvider ×3（E1，P0-B §4 / §5）

```rust
pub struct RemoteVersion {
    pub version: String,          // "3.5" / "7.0"
    pub fetched_at: DateTimeUtc,
    pub source: &'static str,     // "hyp:getGamePackages" / "kuro:index.json" / "degraded"
}
```

| Adapter | 输入 | 输出与要点 |
|---------|------|-----------|
| `HoyoPlayAdapter` | 一次 `GET getGamePackages`（`launcher_id=VYTpXlbWo8`，game_id 参数实际被忽略） | 按 game_id 过滤 `data.game_packages[].main.major.version`；**1 对 3 复用**；region → base 切换（国服 base 待实测 T1；备用 = 国服 mdk content API，P0-B §1.2） |
| `KuroAdapter` | `GET <CDN_BASE>/<appId>_<appKey>/G153/index.json` | `default.config.version`；**端点漂移兜底**：`KRApp.conf`（`base64(XOR(data, 0x63))`）解密恢复常量（P0-B §2.2）；国服常量差异待实测 T2 |
| `DegradedAdapter` | —（终末地） | 恒 `Unknown` + 官方渠道引导（GRYPHLINK 内更新），UI 标注「调研中」（P0-B §3.2） |

**调度与合规（P0-B §5.4）：**

- 触发：应用启动（延迟数秒，不阻塞冷启动 ≤ 3s）+ 手动刷新；设置项可关
- 失败 → `Unknown`，不误报（02 E1 验收）；结果会话内缓存
- 版本比较：自实现**数值点分比较器**（游戏版本非 semver，如 `3.5` / `7.0`）；**比较双方先经 §5.1 归一化**（远程 manifest 版本同样可能携带构建号），在 `(major, minor)` 粒度比较——本地 < 远程 → `UpdateAvailable`。不做归一化会出现本地 `7.0.10.x` 恒大于远程 `7.0` 的静默漏报

### 5.3 WuwaConfigProvider（B1，P0-B §6 键级声明）

**目标文件：** `<游戏根目录>\Wuthering Waves Game\Client\Saved\LocalStorage\LocalStorage.db`（SQLite，单表 `LocalStorage(key, value)`，value 为混合类型：整数或 JSON 文本，按键声明解析）。

**键声明（MVP 全集）：**

| `GameQualitySetting` | JSON | 读 → 反序列化 → 改 `KeyCustomFrameRate` → 写回（`rusqlite` 等价 FastChen 路径） |

INSERT INTO LocalStorage(key, value) VALUES ('CustomFrameRate', ?1)

### 5.4 BackupManager（A8 / B2 / B4）

**备份单元 = 整目录快照**（P0-B §6.1：journal / db2 伴生文件必须覆盖，不能只拷 db）：

```rust
pub struct BackupRecord {
    pub id: BackupId,
    pub installation_id: InstallationId,
    pub tool_id: Option<ToolId>,           // None = 手动备份
    pub trigger: Trigger,                  // Manual | PreModify | PreRestore
    pub files: Vec<FileHash>,              // rel_path / sha256 / size
    pub created_at: DateTimeUtc,
}
```

- **create**：precheck（进程）→ 复制 `declared_paths` 展开的整目录 → 逐文件 SHA256 → 写 `manifest.json` + 落库
- **restore**：precheck → 先做「恢复前备份」（`PreRestore`，任何恢复本身可撤销，02 A8）→ 覆盖 → 逐文件哈希校验
- 存储：`backups/<installation_id>/<backup_id>/`（§6.3）；MVP 全量保留 + 手动清理

### 5.5 EnhancementExecutor：L1 链路状态机（B1–B4）

```
enableTool(wuwa-fps-120)
   │
   ▼
[Gate] 兼容门控（分层，00 §4.4 / P0-C §2.1）：
       Verified / Compatible → 通过
       Unknown · L1 工具   → 拦截 + 显式提示 + 「继续使用」覆盖入口（覆盖动作写日志）
       Unknown · L3 工具   → 硬阻止（02 B7「拦截并阻止」）
       Incompatible / Deprecated → 一律硬阻止 + 原因（B6）
   │
   ▼
[Precheck] 进程 / 写权限（红线 1）
   │
   ▼
[Backup] BackupManager::create(PreModify)     —— B2：无备份不修改（硬性顺序）
   │
   ▼
[Modify] ConfigSource::apply（双键 = 120）      —— B1
   │
   ▼
[Verify] read_back(双键) == 期望                —— B3
   │                    │
   ok                   fail
   │                    ▼
[Applied]          [RollingBack] restore(最新备份) + 哈希校验 —— B4
   │                    │
   ▼                    ▼
收尾事件 + 日志      [RolledBack] 明示「修改失败，已自动恢复原配置」
```

- 状态枚举：`Pending → GatePassed → BackedUp → Modified → Verified | RollingBack → RolledBack`
- Unknown 覆盖（仅 L1）入口位于 S2a Enhancement 卡片，交互规格随 03 下轮对齐补充；覆盖执行同样走完整备份 → 修改 → 验证链路——不因用户选择继续而跳过安全模型
- **每步** = 一次 `tool:apply-step` 事件（驱动 D4 透明卡片）+ 一条结构化日志（00 §9.1，Category = Backup / Modify / Verify / Rollback）
- 执行器内 `catch_unwind`：工具链路任何 panic 转入 RollingBack，**不影响主进程**（00 原则 02 / 12.4 A「Tool 失败不影响 Launcher」）

### 5.8 UnlockerRunner（B7，L3，发行包分离）

**首次启用流程（P0-A §1.3 口径）：**

```
风险告知（版本化文案，全屏确认）
   → 用户显式勾选确认
   → 从 Orbis Releases 独立资产下载（主安装包不含注入器）
   → SHA256 校验（清单 = data/tools/assets.json，随 Orbis 版本分发）
   → 解包至 appdata/tools/genshin-fps-unlock/<version>/
   → tool_state 记录 { asset_version, sha256, granted_at, consent_text_hash }
```

**运行时（与 §5.9 编排协作）：**

- 门控：`compat ∈ {Verified, Compatible}` 且本地版本已知，否则阻止并解释（B7 验收）
- 资产哈希与记录不符 → 拒绝加载（防篡改）
- 解锁器进程失败 / 崩溃 → **降级普通启动 + 明示「本次未解锁」**，绝不阻塞游戏本体（02 B7 边界）
- 上游：34736384/genshin-fps-unlock（MIT，v3.0.4，P0-A §1）；sefinek fork 备选；以外部子进程调用集成，实现可替换（00 §5.2）
- 资产构建管道（上游源码构建 vs 复用上游发行物）见开放问题 Q1
- **Smart App Control 应对**（P0-A §4 指派项）：未签名资产首次运行可能被 Windows SAC 拦截（fork 版已实证，P0-A §1.2）——R4 白名单引导文档必须覆盖解锁器资产本身；根治项 = 代码签名（R4 ②）
- **.NET Runtime 依赖**（P0-A §4 指派项）：上游为 C# / .NET 8——资产打包倾向 **self-contained 发布**（免用户安装运行时，代价约 +70MB 下载体积），随 Q1 构建管道一并定稿

### 5.9 LauncherOrchestrator（A4 / B8）

```
launchGame(installation, opts { skipUnlock })
  1. 状态检查：已在运行 → 拒绝重复启动（A4）
  2. 原神 && 解锁启用 && !skipUnlock：
       兼容门控失败 → 阻止并解释（B7）
  3. spawn 游戏（LaunchSpec：exe + args(region) + cwd）   —— args 待实测 T5
       （原神解锁模式下，游戏创建可能改由解锁器代行，见第 4 步）
  4. （原神）解锁编排——两方案，以 T4 结论定稿：
       方案 A（首选假设，P0-A §1.2「解锁器拉起游戏」）：解锁器作为父进程，
              创建挂起的游戏子进程，注入后恢复——亲子句柄继承可能免除提权
       方案 B：主进程 spawn 游戏后，再 spawn 解锁器附加运行中进程（仅当 T4 证明可行）                            
  5. ProcessMonitor 开始跟踪；PlaytimeSession 开始计时
```

- `skipUnlock` = 「本次不解锁」开关：正常启动且**不改变**工具启用状态（B8 验收）
- `terminateGame`：前置数据损坏风险提示 + 确认 + 日志（A4 边界）

### 5.10 ProcessMonitor 与 PlaytimeTracker（A5 / A6）

- `sysinfo` 进程快照轮询（5s 周期，满足 A5「5 秒内反映」）；匹配 = exe 路径前缀
- 游戏时长口径 = **游戏进程存活时长**（02 A6 边界，UI 明示）
- `playtime_session` 每 30s checkpoint 落库 → Orbis 崩溃 / 被杀，重启后时长不丢（A6 验收）
- 「今日 / 本周」统计按**本地时区自然日界**聚合（A6）
- 进程崩溃 → 状态回落 `Installed` + 写日志（A5）

### 5.11 LogStore（D3）

- `tracing` + 自定义 Layer → JSONL 按日滚动：`logs/orbis.YYYY-MM-DD.log`
- 行结构 = 00 §9.1 schema：`{ ts, source, category, level, message, context, related_game }`
- Source 枚举：`Game / Tool / Launcher / Backup / Update`；Category 枚举：`Detect / Launch / Backup / Modify / Verify / Rollback / Version / Auth`
- 保留 14 天（启动时清理，默认值待确认 §11 Q4）；仅本地，无遥测；D6 查看页 P1（文件可直接打开）

## 8. 降级与错误策略

| 场景 | 行为 | 依据 |
|------|------|------|
| 版本源不可达 / 超时 | `Unknown`，不误报 | 02 E1 验收 |
| 终末地 E1 | 本地版本展示 + 官方渠道引导，标「调研中」 | P0-B §3.2 |
| 种子表缺失 / 损坏 | 兼容查询全部 `Unknown` | 02 C4 验收 |
| 单个 Manifest 损坏 | 该工具不可见，其余正常 | 02 C1 验收 |
| 解锁器下载 / 加载失败 | 阻止启用或降级普通启动 + 明示 | 02 B7 边界 |
| 写权限不足 | precheck 阻止 + 引导 | 02 A8 / B1 |
| 备份失败 | 不进入 Modify（顺序约束） | 02 B2 |
| 工具链路 panic | catch_unwind → 回滚 → 主流程不受影响 | 00 原则 02 |
| 扫描超时 / 权限不足 | 部分结果 + 手动添加引导 | 02 A1 |
| 版本无法识别 | `Unknown`，不显示过期缓存 | 02 A3 |

**总原则：任何降级必须显式可见，禁止静默失败（00 §8.3 不做隐式操作）。**
